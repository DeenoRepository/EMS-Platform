# Мастер-план миграции на новую архитектуру EMS Platform

## 1. Контекст и предпосылки

Текущая реализация системы EMS Platform базируется на монолитной архитектуре (Next.js App Router, единая схема Prisma в [`packages/database/prisma/schema.prisma`](packages/database/prisma/schema.prisma), общие типы в [`packages/shared/src/types.ts`](packages/shared/src/types.ts)). 
С ростом функциональности (EPS, WMS, MRO, PRM) выявились критические архитектурные ограничения:
- **Высокая связанность данных:** Таблицы оборудования, остатков склада и нарядов связаны прямыми внешними ключами. Изменение структуры паспорта оборудования требует рефакторинга складских и ремонтных роутов.
- **Единый контур сбоев:** Ошибка или блокирующая миграция в модуле закупок (PRM) может вывести из строя ядро авторизации и складской модуль (WMS).
- **Сложность масштабирования команды и разработки:** Разработка различных модулей пересекается в одном репозитории, создавая конфликты слияния и монолитные зависимости.

### Целевые параметры системы
- **Пользовательская база:** 50 авторизованных сотрудников предприятия (инженеры, операторы складов, мастера ТОиР, отдел закупок, администраторы).
- **Профиль нагрузки:** Средняя интенсивность, пиковая нагрузка 10–20 RPS, транзакционные операции (списания, перемещения, смена статусов оборудования), пакетная генерация отчетов и актов.
- **Архитектурная модель:** **Microkernel Architecture (Плагинное микроядро) + Event-Driven Bus** с мульти-репозиторной организацией.

## 2. Стратегия миграции (Strangler Fig Pattern)

Переход осуществляется без остановки эксплуатации текущей системы методом постепенного «удушения» монолита (Strangler Fig Pattern):
1. Разворачивается отдельный контур управления агентами (`platform-governance`).
2. Создаются ядро (`platform-shell`) и шина событий (`@platform/contracts`).
3. Доменные модули поочередно переносятся в изолированные репозитории, переводя синхронные междоменные вызовы на асинхронные события шины.
4. На границе между старой системой и новыми модулями устанавливается временный адаптер шины (Event Bridge).

                                        |
+---------------------------------------v---------------------------------------+

                                        |

## 3. Детальные фазы выполнения работ

### Фаза 0: Подготовка контура агентной разработки (Подготовительный этап)
- **Цель:** Изолировать контекст ИИ-агентов от продуктового кода.
- **Действия:**
  1. Создание отдельного приватного репозитория `platform-governance`.
  2. Размещение в нем инструкций, каталога скиллов из [`alirezarezvani/claude-skills`](https://github.com/alirezarezvani/claude-skills), чеклистов качества и скриптов валидации.
  3. Формирование протокола инициализации агента (handshake с запросом репозитория).
- **Критерий завершения (DoD):** Репозиторий `platform-governance` инициализирован; агент при старте сессии запрашивает целевой репозиторий и считывает правила из governance.

### Фаза 1: Разработка платформенных контрактов (`platform-contracts`)
- **Цель:** Задать жесткие границы интерфейсов и протоколов до написания кода реализации.
- **Действия:**
  1. Реализация библиотеки `@platform/contracts` в отдельном репозитории.
  2. Типизация базового ядра: интерфейсы пользователя, сессии, контекста прав доступа.
  3. Реализация абстракции [`EventBus`](packages/shared/src/types.ts:1): `publish()`, `subscribe()`, `unsubscribe()`.
  4. Спецификация контрактов системных и бизнес-событий (Zod schemas).
  5. Разработка набора mock-хелперов для тестирования модулей в TDD-режиме без запуска шины.
- **Критерий завершения (DoD):** 100% покрытие контрактов тестами сериализации/десериализации; пакет опубликован во внутренний реестр/git-подмодуль.

### Фаза 2: Разработка легковесного ядра (`platform-shell`)
- **Цель:** Построить платформу выполнения модулей и хостинга интерфейса.
- **Действия:**
  1. Создание репозитория `platform-shell`.
  2. Модульный загрузчик (Dynamic Module Loader): чтение манифестов модулей, инициализация схем БД, запуск фоновых подписчиков.
  3. Механизм Service & Extension Registry (SPI).
  4. Встроенная база пользователей и ролевая модель (RBAC Guard).
  5. UI App Shell: базовая разметка, авторизационный экран, динамическое монтирование маршрутов и навигации зарегистрированных модулей.
- **Критерий завершения (DoD):** Ядро стартует, загружает тестовый пустой модуль-заглушку, отображает базовый UI, отрабатывает аутентификацию.

### Фаза 3: Разработка базовых расширений ядра (`ext-*`)
- **Цель:** Перенос инфраструктурных сервисов из текущего монолита в форму расширений.
- **Компоненты:**
  * `ext-auth-ldap` — провайдер авторизации через Active Directory / OpenLDAP (вынос из [`packages/auth/src/ldap.ts`](packages/auth/src/ldap.ts)).
  * `ext-storage-s3` / `ext-storage-local` — провайдер файлового хранилища актов, паспортов и инструкций.
  * `ext-audit-syslog` — структурированный аудит действий пользователей (вынос из [`packages/auth/src/audit.ts`](packages/auth/src/audit.ts)).
- **Критерий завершения (DoD):** Расширения подключаются через файл конфигурации ядра без изменения исходного кода ядра.

### Фаза 4: Поэтапная миграция бизнес-модулей в TDD-режиме
Каждый модуль создается в отдельном репозитории, имеет собственную изолированную БД/схему и общается со внешним миром только через события.

#### 4.1. Модуль EPS (Electronic Passport System) — `module-eps`
- **Функционал:** Карточки оборудования, технические характеристики, классификаторы, узлы и агрегаты, генерация инвентарных номеров.
- **События на выход:** `eps.equipment.created`, `eps.equipment.updated`, `eps.equipment.decommissioned`.
- **TDD:** Тестирование генераторов штрихкодов, валидаторов паспортов, расчета износа.

#### 4.2. Модуль WMS (Warehouse Management System) — `module-wms`
- **Функционал:** Складской учет, ячеистое хранение, партии, приход, расход, инвентаризация, внутренние перемещения.
- **События на вход:** Слушает `prm.order.received` (оприходование ТМЦ по заказу закупки).
- **События на выход:** `wms.stock.reserved`, `wms.stock.issued`, `wms.stock.depleted`.
- **TDD:** Тестирование алгоритмов списания (FIFO), резервирования остатков, расхождений при инвентаризации.

#### 4.3. Модуль MRO (Maintenance, Repair, Overhaul) — `module-mro`
- **Функционал:** Планы и графики ТОиР, периодические регламенты, наряды-допуски, учет дефектов, журнал простоев.
- **События на вход:** Слушает `eps.equipment.decommissioned`, `wms.stock.issued`.
- **События на выход:** `mro.work_order.created`, `mro.spare_parts.requested`, `mro.maintenance.completed`.
- **TDD:** Тестирование калькулятора наработки часов, планировщика ТО, проверки квалификаций исполнителей.

#### 4.4. Модуль PRM (Procurement & Requests) — `module-prm`
- **Функционал:** Потребности цехов, заявки на закупку, согласование по матрице лимитов, контроль поставок.
- **События на вход:** Слушает `mro.spare_parts.requested`, `wms.stock.depleted`.
- **События на выход:** `prm.request.approved`, `prm.order.placed`, `prm.order.received`.
- **TDD:** Тестирование матрицы многоступенчатых согласований, агрегации однотипных потребностей.

### Фаза 5: Оркестрация, E2E-верификация и ввод в эксплуатацию
- **Действия:**
  1. Создание репозитория `platform-distribution` с `docker-compose.prod.yml`, объединяющим ядро, модули и PostgreSQL.
  2. Скрипт миграции данных из старой БД монолита в изолированные схемы новых модулей.
  3. Сквозные интеграционные тесты шины событий между всеми четырьмя модулями.
  4. Нагрузочное тестирование сценариев одновременной работы 50 пользователей.
  5. Переключение DNS/трафика на новый дистрибутив.

## 4. Матрица рисков и меры нейтрализации

| Риск | Вероятность | Влияние | Стратегия предотвращения |
|---|---|---|---|
| **Рассинхронизация данных между модулями при потере событий** | Низкая | Высокая | Использование транзакционного Outbox-паттерна на уровне каждого модуля и идемпотентности обработчиков событий |
| **Сложность локальной разработки мульти-репо** | Средняя | Средняя | Единый `docker-compose.dev.yml` в `platform-distribution` с монтированием директорий через volume |
| **Случайное попадание инструкций ИИ в рабочий код** | Средняя | Высокая | Автоматический pre-commit хук и CI-линтер в репозиториях, блокирующий файлы с паттернами `.agents`, `AGENTS.md`, `CLAUDE.md` |
| **Регрессии бизнес-логики при переносе** | Средняя | Высокая | Обязательный перенос существующих unit-тестов из [`packages/shared/src/shared-logic.test.ts`](packages/shared/src/shared-logic.test.ts) и доменных сервисов с валидацией входных/выходных контрактов |
