# Регламент разработки для ИИ-агентов (Agent Governance & Rules)

Данный документ устанавливает обязательные инженерные стандарты, протокол взаимодействия и правила выполнения задач для ИИ-агентов, работающих над кодовой базой EMS Platform.

---

## 1. Фундаментальный принцип: Чистота продуктовых репозиториев

1. **Полный запрет на упоминание ИИ и агентных систем:**
   * В рабочих репозиториях (`platform-shell`, `platform-contracts`, `module-*`, `ext-*`, `platform-distribution`) **СТРОГО ЗАПРЕЩЕНО** создавать или коммитить:
     * Каталоги `.agents/`, `.claude/`, `.ai/`
     * Файлы `AGENTS.md`, `CLAUDE.md`, `PROMPTS.md`, `.cursorrules`
     * Комментарии в коде с упоминанием AI, Claude, LLM, Prompts, автогенерации кода.
2. **Изоляция в `platform-governance`:**
   * Все инструкции, правила, чеклисты, описания скиллов и конфигурации агентных сред хранятся исключительно в закрытом служебном репозитории `platform-governance`.
   * Агент считывает этот репозиторий в память в начале сессии как контекст правил и применяет их к целевому продуктовому репозиторию.
3. **Автоматический аудит чистоты кодовой базы:**
   * Каждый коммит проверяется на отсутствие запрещенных файлов и маркеров. При обнаружении маркерных строк или файлов коммит немедленно блокируется.

## 2. Протокол инициализации задачи (Handshake Protocol)

При старте новой сессии или инициализации работы над модулем/расширением/ядром агент **ОБЯЗАН** выполнить процедуру рукопожатия (Handshake) до совершения любых файловых операций:

```
+-------------------------------------------------------------------------------+
|                       ШАГ 1: Запрос контекста репозитория                     |
|  Агент запрашивает:                                                           |
|  - URL или локальный путь целевого репозитория                                |
|  - Тип компонента (Shell / Contract / Module / Extension)                     |
|  - Целевую ветку (например, `main` или `feature/issue-123`)                   |
+---------------------------------------+---------------------------------------+
                                        |
+---------------------------------------v---------------------------------------+
|                       ШАГ 2: Запрос постановки задачи                         |
|  Агент запрашивает:                                                           |
|  - Идентификатор задачи / User Story / Issue                                  |
|  - Acceptance Criteria (критерии приёмки)                                     |
|  - Ограничения контрактов (события, входы, выходы)                            |
+---------------------------------------+---------------------------------------+
                                        |
+---------------------------------------v---------------------------------------+
|                       ШАГ 3: Синхронизация и базовый аудит                    |
|  Агент выполняет:                                                             |
|  - `git fetch && git status`                                                  |
|  - Проверку чистоты рабочего дерева (clean working tree)                      |
|  - Запуск существующего набора тестов (`pnpm test` -> Green Baseline)          |
+-------------------------------------------------------------------------------+
```

## 3. Режим разработки: Test-Driven Development (TDD)

### 3.1. Обязательный TDD-цикл
Для всех доменных сервисов, расчетов, моделей данных, обработчиков событий и API контроллеров агент работает строго по итерациям:

1. **RED (Красный этап):**
   * Написание изолированного unit- или integration-теста, описывающего ожидаемое поведение новой функции или контракта.
   * Запуск тестового раннера: убедиться, что тест **падает именно по причине отсутствия функциональности**, а не из-за синтаксической ошибки импорта.
2. **GREEN (Зеленый этап):**
   * Написание минимально достаточного кода реализации для прохождения теста.
   * Запуск теста: подтверждение перехода в зеленый статус.
3. **REFACTOR (Рефакторинг):**
   * Устранение дублирования, оптимизация производительности, проверка строгости типов TypeScript.
   * Повторный запуск тестов: гарантия отсутствия регрессий.

### 3.2. Особое правило: Освобождение UI от тестов
* **Компоненты интерфейса (React, MUI, CSS-in-JS, страницы Next.js) тестами НЕ покрываются.**
* Обоснование: Тестирование верстки и стилей создает избыточную хрупкость и замедляет эволюцию визуальной части.
* Вся UI-логика (состояния, маппинги, фильтры, трансформация DTO) обязана выноситься в чистые вспомогательные функции (pure functions / hooks) вне JSX, и именно эти чистые функции подлежат обязательному TDD-тестированию.

## 4. Регламент управления репозиториями и Git-коммитов

1. **Обязательная фиксация:**
   * Каждая успешно решенная задача или завершенный логический этап **ОБЯЗАНЫ** завершаться созданием Git-коммита.
   * Запрещено оставлять незакоммиченные изменения в рабочей директории при завершении диалога.
2. **Формат сообщений Conventional Commits:**
   * `feat(<scope>): <описание>` — новый функционал / новый обработчик события / сервис
   * `fix(<scope>): <описание>` — исправление дефекта логики
   * `refactor(<scope>): <описание>` — оптимизация без изменения публичного API
   * `test(<scope>): <описание>` — добавление или доработка тестов
   * `chore(<scope>): <описание>` — правка конфигураций сборки, зависимостей
   * *Примеры:*
     * `feat(wms): implement FIFO stock dispatch calculation service`
     * `test(mro): add test suite for maintenance interval generator`
     * `fix(eps): prevent negative equipment wear coefficients`
3. **Инженерный стиль кода:**
   * Код пишется от лица опытного Senior-разработчика.
   * Переменные, функции, типы и документация — на профессиональном техническом английском языке.
   * Доменная документация и отчеты — на русском или английском в соответствии с проектом.

## 5. Стандарты архитектурной изоляции кода модулей

При написании кода бизнес-модуля агент обязан проверять:

1. **Отсутствие кросс-модульных импортов:**
   * ❌ `import { EquipmentService } from '@platform/module-eps'` (ЗАПРЕЩЕНО).
   * ✅ Получение данных только через публикацию запроса в шину или подписку на события `@platform/contracts`.
2. **Изоляция базы данных:**
   * Все запросы (Prisma / Kysely / raw SQL) должны оперировать только таблицами своей схемы (например, `wms.*`).
   * Запрещено создавать Foreign Key на таблицы чужих схем (например, `REFERENCES eps.equipment(id)`).
3. **Обработка сбоев шины:**
   * Все исходящие события должны сохраняться в локальную таблицу `outbox` в рамках транзакции сохранения бизнес-сущности.
