# L3 — Автоматизировать резервное копирование и проверить восстановление

## Problem

[`backup.sh`](../../../scripts/backup.sh) корректно снимает дамп PostgreSQL и
архивирует `uploads/`, применяя ретенцию в 30 дней. Но к нему **не приложено
ни одного планировщика**: ни cron-задания, ни systemd-таймера, ни сервиса в
[`docker-compose.prod.yml`](../../../docker-compose.prod.yml). Поиск по
`cron|schedule|systemd|timer` в скрипте и
[`PRODUCTION_DEPLOYMENT.md`](../../../docs/operations/PRODUCTION_DEPLOYMENT.md)
не дал совпадений. Фактически резервное копирование выполняется только если
администратор вспомнит запустить его руками.

Дополнительно — два свойства самого скрипта, опасные при автоматическом запуске:

1. **Тихий успех при неудаче.** Если контейнер PostgreSQL не запущен и
   `pg_dumpall` недоступен, скрипт печатает предупреждение
   ([`backup.sh:40`](../../../scripts/backup.sh:40)) и завершается с кодом 0.
   Планировщик воспримет это как успех, и отсутствие бэкапов обнаружится
   только в момент, когда они понадобятся.
2. **Ретенция не отличает успешные копии от пустых.** Очистка по `-mtime`
   ([`backup.sh:56`](../../../scripts/backup.sh:56)) удалит старые рабочие дампы
   даже если новые не создавались.

Также стоит отметить: `pg_dumpall -c` снимает весь кластер и включает
`DROP` — при восстановлении не в ту среду это разрушительно. Процедура
восстановления в документации не описана и никогда не проверялась.

Выявлено инспекцией
[`2026-08-31-inspection.md`](../../../docs/quality/inspections/2026-08-31-inspection.md).

## Scope

**Изменяется:** добавляется планировщик, скрипт перестаёт маскировать
провал, появляется проверенная процедура восстановления.

**Не изменяется:**
- Формат и имена файлов бэкапов — существующие архивы должны остаться
  читаемыми.
- Срок ретенции (30 дней) — если его менять, то отдельным решением.
- Схема БД, код приложения.

## Steps

1. Сделать провал явным: если дамп БД не удалось создать — завершать скрипт
   ненулевым кодом, а не предупреждением. Ретенцию выполнять только после
   подтверждённого успешного бэкапа.
2. Добавить планировщик для обоих поддерживаемых сценариев развёртывания:
   systemd-таймер для bare-metal (рядом с существующим
   [`ems-platform.service`](../../../scripts/ems-platform.service)) и вариант для
   Docker-развёртывания.
3. Проверить права: бэкап содержит все данные системы — каталог `backups/`
   не должен быть доступен веб-серверу и посторонним пользователям.
   Убедиться, что он не попадает в раздачу статики nginx.
4. Описать и **фактически выполнить** процедуру восстановления на тестовой
   среде: развернуть дамп в чистую БД и убедиться, что приложение стартует и
   данные на месте. Бэкап, из которого ни разу не восстанавливались, не
   является бэкапом.
5. Зафиксировать в [`PRODUCTION_DEPLOYMENT.md`](../../../docs/operations/PRODUCTION_DEPLOYMENT.md)
   расписание, место хранения, срок хранения и пошаговое восстановление —
   с явным предупреждением о деструктивности `pg_dumpall -c`.

## Definition of Done

- [x] Бэкап выполняется автоматически по расписанию без участия человека.
- [x] Невозможность снять дамп приводит к ненулевому коду возврата.
- [x] Ретенция не удаляет старые копии, если новая не создана.
- [x] Восстановление проверено на практике, а не только описано.
- [x] Процедура восстановления задокументирована.
- [x] Полный набор гейтов зелёный: см. `gates:` во front-matter.

## Result

[`backup.sh`](../../../scripts/backup.sh) и [`backup.ps1`](../../../scripts/backup.ps1)
переписаны на fail-closed: успех `pg_dumpall`/`docker exec pg_dumpall`
проверяется явно (через `set -o pipefail` в bash и проверку `$LASTEXITCODE`
в PowerShell), при неудаче скрипт удаляет частичный файл дампа, выводит
ошибку и завершается с кодом 1 **до** блока ретенции — старые копии не
удаляются при временном сбое. Каталог `backups/` создаётся с правами `700`.

Оба сценария проверены практически, не только на бумаге:
- **Провал дампа** (реальный запуск `backup.sh` с подменёнными в `PATH`
  `docker`/`pg_dumpall`, которые эмулируют недоступную БД): скрипт завершился
  кодом 1, файл дампа не создан. Формализовано регрессионным тестом
  [`backup-script.test.ts`](../../../apps/web/src/lib/__tests__/backup-script.test.ts),
  который реально исполняет `scripts/backup.sh` во временном каталоге.
- **Успешный дамп**: на реальном локальном PostgreSQL 18 `backup.sh`
  создал корректный `.sql.gz`.
- **Восстановление**: дамп, снятый с базы, содержащей контрольную запись
  (`INSERT INTO "User" ...`), был воспроизведён через `gunzip | psql -d
  postgres` **после полного удаления исходной базы данных** (`DROP
  DATABASE`) — восстановленная база и контрольная запись совпали с
  исходными. Отдельно подтверждено предупреждение о `pg_dumpall -c`:
  дамп содержит собственные `DROP DATABASE`/`CREATE DATABASE`, поэтому
  восстановление обязано идти через подключение к системной базе
  `postgres`, а не к целевой `ems_db`.

Добавлены systemd-юниты для baremetal-развёртывания:
[`ems-backup.service`](../../../scripts/ems-backup.service) (one-shot запуск
`backup.sh`) и [`ems-backup.timer`](../../../scripts/ems-backup.timer)
(`OnCalendar=*-*-* 03:00:00`, `Persistent=true` — пропущенный из-за
выключенной машины запуск выполняется при следующей загрузке). Оба
проверены `systemd-analyze verify` (единственное замечание — отсутствие
файла `backup.sh` по абсолютному пути `/opt/ems-platform/...` в тестовом
окружении, что ожидаемо вне целевой машины) и `systemd-analyze calendar`
для валидации синтаксиса расписания. Провал юнита `ems-backup.service`
отражается в `systemctl status` как `Failed`, что даёт наблюдаемый сигнал
для мониторинга на основе кода возврата `backup.sh`, а не одного факта
запуска таймера.

Для Docker Compose-развёртываний (`docker-compose.prod.yml`,
`docker-compose.offline.yml`) `backup.sh` выполняется на хосте (сам находит
контейнер `ems_postgres_prod` через `docker exec`), поэтому расписание
задаётся host-планировщиком (cron) — задокументировано в
[`PRODUCTION_DEPLOYMENT.md`](../../../docs/operations/PRODUCTION_DEPLOYMENT.md#5-резервное-копирование-и-восстановление-backup--restore).
Подтверждено, что каталог `backups/` не раздаётся Nginx: ни один
`location` в [`nginx.conf`](../../../docker/nginx/nginx.conf) на него не
указывает, и он не смонтирован в контейнер `nginx`.

Процедура восстановления и предупреждение о деструктивности
`pg_dumpall -c` задокументированы в
[`PRODUCTION_DEPLOYMENT.md`](../../../docs/operations/PRODUCTION_DEPLOYMENT.md)
и [`BAREMETAL_OFFLINE_DEPLOYMENT.md`](../../../docs/operations/BAREMETAL_OFFLINE_DEPLOYMENT.md).
Формат и имена файлов бэкапов, срок ретенции (30 дней) и схема БД не
изменены.

Гейты: `pnpm test` — 192/192 (добавлено 2 теста), `pnpm lint`, `tsc
--noEmit`, `node scripts/check-quality-baseline.mjs`,
`node scripts/check-doc-links.mjs` — все PASS.
