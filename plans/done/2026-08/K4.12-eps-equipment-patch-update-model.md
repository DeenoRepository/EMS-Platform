# K4.12 — Декомпозировать модель обновления оборудования EPS

## Problem

Повторное измерение после K4.11 показало verified business candidate
[`PATCH()`](../../../apps/web/src/app/api/eps/equipment/[id]/route.ts:108) с `cx 26`.
Route одновременно валидирует body, нормализует дату, выбирает ветку согласования
или прямого обновления и строит повторяющиеся Prisma payloads.

Presentation-only и уже закрытые кандидаты в этот stage не входят.

## Verified map

- [KNOWN] Единственный PATCH route находится в [`route.ts`](../../../apps/web/src/app/api/eps/equipment/[id]/route.ts:108).
- [KNOWN] Клиентские consumers вызывают тот же URL через [`saveEquipmentEdit()`](../../../apps/web/src/components/eps/equipment-passport-actions.ts:137) и [`submitEquipmentForApproval()`](../../../apps/web/src/components/eps/equipment-passport-actions.ts:185).
- [KNOWN] [`updateSchema`](../../../apps/web/src/app/api/eps/equipment/[id]/route.ts:91) остаётся в route, поскольку Zod validation и error response являются HTTP-контрактом.
- [KNOWN] Pure date parsing and normalized proposal/update payload construction can be extracted without moving auth, rate limiting, Prisma transactions, approvals, audit logging, or response handling.
- [KNOWN] No new dependency is required; the route already uses Zod and Prisma types.

## Scope

Вынести только pure-модель подготовки нормализованных значений equipment PATCH:
безопасный разбор даты, выбор effective commission date, proposed data для approval
ветки и повторяющиеся equipment update data fields. Сохранить все существующие
условия, nullable semantics, tag handling, custom field JSON cloning, approval
payload, transactions, authorization, audit logging и response contracts.

Не менять GET/DELETE, схему Zod, API URL/method, permissions, rate limiting,
Prisma calls/transactions, K6 или другие K4 candidates.

## Steps

1. Extract the pure EPS equipment patch update model beside the route.
2. Replace only equivalent inline normalization/payload construction in `PATCH()`.
3. Add focused tests for date parsing, approval proposal mapping, and direct update mapping.
4. Re-measure `PATCH()`, run targeted/full tests, lint, web TypeScript, quality, and docs checks.
5. Close and move this story after the successful implementation commit.

## Definition of Done

- [x] Real `PATCH()` complexity is reduced by extracting normalized payload construction; remaining approval and transaction orchestration stays in the route.
- [x] Focused tests cover valid/invalid/empty dates, proposal mapping, and direct update mapping.
- [x] API, permissions, rate limiting, Prisma semantics, transactions, approval behavior, audit logging, and response contract are unchanged.
- [x] Targeted tests, full tests, lint, web TypeScript, quality baseline, and docs link check are green.
- [x] Story is closed, indexed, and committed.

## Ponytail check

Rung 1 does not apply: equipment updates and approval payloads are active business
behavior. Rungs 2–4: native date arithmetic, object construction, existing Zod,
Prisma, and test runner are sufficient; no new dependency or generic route
framework is justified. Rung 6: minimum implementation is one neighboring pure
model plus focused tests, leaving HTTP/security/database orchestration in the route.

## Result

Implemented and closed the bounded pure-model extraction in commit `8b13c9c`. [`PATCH()`](../../../apps/web/src/app/api/eps/equipment/[id]/route.ts:113) now delegates date normalization, approval proposal construction, and Prisma-compatible equipment update data to [`patch-update-model.ts`](../../../apps/web/src/app/api/eps/equipment/[id]/patch-update-model.ts). Authentication, rate limiting, Zod validation, transactions, approval creation, audit logging, and response handling remain in the route. Targeted tests pass (4), full tests pass (181), lint passes, web TypeScript passes, quality baseline passes, and docs links pass. The story is moved to `plans/done/2026-08/` and indexed.
