# L4 — Добавить E2E smoke-покрытие критических пользовательских сценариев

## Problem

В репозитории нет ни одного сквозного теста: каталоги `e2e/`, `tests/`,
`playwright.config.*` отсутствуют, Playwright не входит в зависимости
[`apps/web/package.json`](../../../apps/web/package.json). Существующие тесты
(`*.test.ts`) — юнит-уровня: домен, RBAC, безопасность, чистые функции.

Это осознанный компромисс, а не дефект: юнит-тесты покрывают самое рискованное
(права доступа, фильтры, парсинг). Но при значительном объёме фронтенда в
`apps/web/src` регрессии интерфейса — сломанный роут, упавший рендер, разорванная
цепочка «логин → страница → действие» — сейчас не ловятся ничем, кроме ручной
проверки. Юнит-тест на функцию остаётся зелёным, даже если страница, которая её
вызывает, не открывается.

Скилл [`playwright-pro`](../../../.agents/skills/playwright-pro/SKILL.md) в проекте
уже установлен, но не задействован.

Выявлено инспекцией
[`2026-08-31-inspection.md`](../../../docs/quality/inspections/2026-08-31-inspection.md).

## Scope

**Изменяется:** добавляется E2E-раннер и узкий набор smoke-сценариев.

**Не изменяется:**
- Существующие юнит-тесты и [`test-runner.mjs`](../../../scripts/test-runner.mjs) —
  E2E запускается отдельной командой, не смешиваясь с быстрым юнит-прогоном.
- Прикладной код. Если сценарий не проходит из-за отсутствия стабильных
  селекторов, добавление `data-testid` допустимо, изменение поведения — нет.
- Обязательность прохождения в CI на первом этапе: сначала сценарии должны
  доказать стабильность, иначе флаки обесценят гейт.

## Steps

1. Подключить Playwright и конфигурацию, изолированную от юнит-раннера.
2. Решить вопрос тестовых данных: E2E требует поднятой БД и известного
   пользователя. Это главное препятствие — определить, используется ли
   отдельная эфемерная БД с сидом
   ([`seed.ts`](../../../packages/database/src/seed.ts)) или контейнер на время
   прогона. Без воспроизводимого состояния сценарии будут флакать.
3. Покрыть **минимальный** набор, а не всё подряд:
   - вход в систему и выход;
   - открытие ключевых разделов (EPS, WMS, MRO) под пользователем с правами;
   - отказ в доступе для пользователя без прав — сценарий, дублирующий на
     сквозном уровне то, что юнит-тесты проверяют на уровне RBAC;
   - один сквозной бизнес-сценарий создания сущности.
4. Прогнать набор многократно, отсеять нестабильные сценарии до включения в
   регулярный запуск.
5. Только после подтверждённой стабильности — добавить шаг в
   [`ci.yml`](../../../.github/workflows/ci.yml) и внести раннер в
   [`scripts/README.md`](../../../scripts/README.md) с указанием предусловий
   (БД, сид, сборка).

## Definition of Done

- [x] E2E-набор запускается одной командой и не требует ручной подготовки
      сверх задокументированной.
- [x] Покрыты: логин, доступ к ключевым разделам, отказ по правам,
      один бизнес-сценарий.
- [x] Набор проходит стабильно при повторных прогонах.
- [x] Предусловия описаны в [`scripts/README.md`](../../../scripts/README.md).
- [x] Юнит-прогон `pnpm test` не замедлился и не зависит от E2E.
- [x] Полный набор гейтов зелёный: см. `gates:` во front-matter.

## Result

Подключён Playwright (`@playwright/test`) как devDependency **только**
`apps/web` (не корневого `package.json`), с изолированным
[`playwright.config.ts`](../../../apps/web/playwright.config.ts): отдельный
порт (3100), `webServer` запускает `next start` (продакшен-сборку, не
`next dev`), не пересекается с `scripts/test-runner.mjs`.

Вопрос тестовых данных (Step 2 плана) решён через
[`apps/web/e2e/global-setup.ts`](../../../apps/web/e2e/global-setup.ts):
перед прогоном создаётся **отдельная эфемерная БД** `ems_e2e_test`
(никогда не dev/prod база), к ней применяются те же версионированные
миграции Prisma, что и в production (`migrate deploy`, см.
[L2](L2-prisma-migration-baseline.md)), затем сидируются
права/роли и два детерминированных пользователя: `e2e_admin` (роль admin,
все права) и `e2e_guest` (роль guest, ноль прав — фикстура для проверки
отказа по RBAC). [`global-teardown.ts`](../../../apps/web/e2e/global-teardown.ts)
удаляет базу после прогона, предварительно завершая зависшие сессии
Prisma-пула `next start` (`pg_terminate_backend`) — без этого `DROP
DATABASE` падал с ошибкой Postgres 55006.

Покрыт минимальный набор (Step 3): вход и выход
([`login.spec.ts`](../../../apps/web/e2e/login.spec.ts), включая отказ по
неверному паролю), доступ к EPS/WMS/MRO под администратором и отказ по
правам для гостя, включая редирект от `/admin/users`
([`module-access.spec.ts`](../../../apps/web/e2e/module-access.spec.ts)),
сквозной бизнес-сценарий создания паспорта оборудования через мастер и
проверка его появления в реестре
([`equipment-create.spec.ts`](../../../apps/web/e2e/equipment-create.spec.ts)).

Стабильность (Step 4) подтверждена **тремя подряд полными прогонами**
всех 9 тестов на реальном локальном PostgreSQL — 27 успешных выполнений,
0 флаки. В процессе отладки исправлены две реальные проблемы, а не
подогнаны ожидания: строгий режим Playwright ловил, что `getByLabel('Пароль')`
неоднозначно резолвился и на текстовое поле, и на кнопку «Показать
пароль» (исправлено на `#password`), а тест отказа по RBAC изначально
проверял отсутствие заголовка страницы, который на самом деле рендерится
всегда — исправлено на проверку реального текста `EmptyState`
(«Доступ ограничен»).

Изменение `pnpm build`/`pnpm test`/`pnpm lint`/`tsc --noEmit` — все
по-прежнему проходят и не включают `apps/web/e2e/`
(ESLint сканирует только `src`, ярлык юнит-раннера ищет только
`*.test.ts`/`*.test.tsx`). Предусловия и команда запуска задокументированы
в [`scripts/README.md`](../../../scripts/README.md) (раздел «E2E smoke tests»),
включая переменные `E2E_DB_*` и `E2E_KEEP_DB`.

CI-шаг сознательно не добавлен на этом этапе — согласно Scope story, гейт
должен быть введён только после подтверждённой стабильности в реальном
CI-окружении, а не только локально.
