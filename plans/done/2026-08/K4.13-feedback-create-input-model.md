# K4.13 — Декомпозировать разбор входных данных создания обращений feedback

## Problem

Текущее измерение quality checker после закрытия K4.12 показывает verified
business candidate [`POST()`](../../apps/web/src/app/api/feedback/route.ts:121)
с `cx 27` / 58 строками. Обработчик совмещает разбор JSON и multipart входа,
нормализацию полей и валидационные проверки перед Prisma и файловыми side effects.

Presentation-only boundaries и unrelated K4/K6 work не входят в scope.

## Verified map

- [KNOWN] Единственный HTTP handler создания feedback находится в
  [`route.ts`](../../apps/web/src/app/api/feedback/route.ts:121).
- [KNOWN] Handler принимает JSON и `multipart/form-data`, включая `files`.
- [KNOWN] После разбора входа route использует только нормализованные `title`,
  `description`, `type`, `module`, `priority`, `pageUrl`, `browserInfo` и
  `uploadedFiles`.
- [KNOWN] Prisma ticket creation, attachment persistence, admin notifications,
  audit logging, auth, rate limiting и response contract должны остаться в route.
- [KNOWN] Existing test runner discovers tests only from packages/auth/src and
  apps/web/src/lib/__tests__; a focused test may use the existing discovered
  location without adding a new test framework.
- [KNOWN] No new dependency is required; the stage can use Web API types and
  native JSON/string operations.

## Scope

Вынести только pure parsing/normalization helpers для уже разобранных JSON и
multipart values, не меняя HTTP contract или downstream Prisma/file behavior.
Добавить focused tests for default values, trimmed text, optional fields and
invalid browser-info fallback where the helper boundary permits.

Не менять API URL/method, auth, rate limiting, permissions, Prisma semantics,
file storage, notifications, audit logging, UI, K6 или другие K4 candidates.

## Steps

1. Extract a minimal input model beside the feedback route.
2. Replace only equivalent inline input parsing in `POST()`.
3. Add focused tests for JSON/default and multipart field mapping.
4. Re-measure `POST()`, run targeted/full tests, lint, web TypeScript, quality,
   and docs checks.
5. Close and move this story after the successful implementation commit.

## Definition of Done

- [x] Real feedback `POST()` complexity is reduced by extracting input parsing,
  or the remaining complexity is documented as an orchestration boundary.
- [x] Existing JSON/multipart field defaults and trimming behavior are unchanged.
- [x] Focused tests cover the extracted input model branches.
- [x] Full gates are green: test, lint, tsc, check:quality, check:docs.
- [x] Story is closed, indexed, and committed with one Conventional Commit.

## Ponytail check

Rung 1 does not apply: feedback creation is active business behavior.
Rungs 2–4: existing Web APIs, native JSON parsing and the repository test runner
are sufficient; no new dependency or generic request framework is justified.
Rung 6: minimum implementation is one neighboring pure input model plus focused
tests, leaving authorization, persistence, uploads, notifications and audit in
the route.

## Result

Closed after verified reconciliation at HEAD `069f967`. The committed stage
extracts JSON and multipart parsing into
[`input-model.ts`](../../apps/web/src/app/api/feedback/input-model.ts), keeps
feedback persistence, uploads, notifications, audit, authorization, rate
limiting, and response behavior in the route, and adds focused tests in
[`feedback-input-model.test.ts`](../../apps/web/src/lib/__tests__/feedback-input-model.test.ts).
The working tree was clean before this documentation closeout; the
implementation and tests were already present in commit `069f967`.
