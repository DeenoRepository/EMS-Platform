# K4.11 — Декомпозировать модель обновления SRM-заявки

## Problem

Повторное измерение после K4.10 показывает проверенный business-кандидат
[`PATCH()`](../../apps/web/src/app/api/srm/issues/[id]/route.ts:87) с `cx 26`.
Обработчик одновременно строит частичное обновление, определяет переход в
resolved-состояние и рассчитывает производные поля даты/простоя, после чего
выполняет Prisma update и побочные обновления оборудования/аудита.

Численно более высокие результаты для presentation boundaries и ложный результат
[`handleOpenDetails()`](../../apps/web/src/app/srm/page.tsx:244) не входят в scope:
чтение исходника показывает, что последний является трёхстрочным state setter.

## Verified map

- [KNOWN] Единственный HTTP consumer PATCH — [`handleSaveQuickUpdates()`](../../apps/web/src/components/srm/SrmIssueDetailsDrawer.tsx:70), который отправляет `status`, `resolutionNotes`, `downtimeMinutes` и `assignee` на `/api/srm/issues/{id}`.
- [KNOWN] [`PATCH()`](../../apps/web/src/app/api/srm/issues/[id]/route.ts:87) также поддерживает остальные разрешённые поля body и сохраняет их через Prisma; API, RBAC и rate limiting должны остаться в route.
- [KNOWN] Resolved-переход зависит от текущего статуса, `resolvedDate`, `downtimeMinutes` и `createdDate`; это бизнес-семантика, которую можно вынести в pure update model без доступа к Prisma.
- [KNOWN] Equipment status update и audit-log являются отдельными side effects после update и в эту stage не входят.
- [KNOWN] Unit-тесты автоматически обнаруживаются [`scripts/test-runner.mjs`](../../scripts/test-runner.mjs:27) из `apps/web/src/lib/__tests__`.
- [KNOWN] No new dependency is required; the model uses TypeScript types and native date arithmetic.

## Scope

Вынести только pure-модель подготовки `dataToUpdate` и derived resolved fields из
SRM PATCH handler в соседний модуль. Сохранить все поддерживаемые поля partial
update, resolved-status matching, resolved-date creation и downtime fallback.
Добавить focused tests на обычные поля, resolved transition, existing resolved
issue, explicit downtime и non-resolved update.

Не менять route authentication, rate limiting, request URL/method, Prisma calls,
equipment status side effect, audit logging, response payloads, UI, database schema,
K6 или другие K4 candidates.

## Steps

1. Extract the pure SRM issue patch update model with the existing Prisma-compatible shape.
2. Replace only inline update-field and resolved-derivation logic in `PATCH()`.
3. Add focused tests for every model branch and preserve route contracts.
4. Re-measure `PATCH()`, run targeted/full tests, lint, web TypeScript, quality, and docs checks.
5. Close and move this story to `plans/done/2026-08/` after the successful implementation commit.

- [x] Focused tests cover partial fields and all resolved/downtime derivation branches.

## Ponytail check

Rung 1 does not apply: SRM issue status/resolution updates are active business behavior.
Rungs 2–4: native object construction/date arithmetic and existing test runner are
sufficient; no new dependency or generic route framework is justified. Rung 6:
minimum implementation is one neighboring pure model plus focused tests, leaving
Prisma and side effects in the route.

Focused tests pass (4), full tests pass (177), lint passes, web TypeScript passes, quality baseline passes, and docs links pass. The story is moved to `plans/done/2026-08/` and indexed.
