# P3 — Исправить переходы из уведомлений PRM к заявке

## Problem

PRM создавал уведомления со ссылкой вида `/prm/<requestId>` как при смене
статуса в [`executeStatusTransition()`](../../../apps/web/src/lib/prm-transition-handler.ts:46),
так и после регистрации поставки в
[`POST()`](../../../apps/web/src/app/api/prm/requests/[id]/deliveries/route.ts:75).
Центр уведомлений без преобразования передаёт `link` в
[`router.push()`](../../../apps/web/src/components/layout/NotificationCenter.tsx:95).
При этом PRM имеет только реестровую страницу
[`PrmRegistryPage()`](../../../apps/web/src/app/prm/page.tsx:562), а детали заявки
открываются локальным состоянием диалога в
[`PrmRegistryContent()`](../../../apps/web/src/app/prm/page.tsx:86); отдельного маршрута
`apps/web/src/app/prm/[id]/page.tsx` в дереве не было. Поэтому ссылка из
уведомления указывала на несуществующую страницу и не открывала карточку заявки.

## Scope

**Входит в scope:**

- Зафиксировать единый существующий маршрут уведомлений PRM через `/prm` с
  query-параметром идентификатора заявки, без создания отдельной detail page.
- На странице реестра прочитать deep-link параметр, загрузить заявку через
  существующий [`GET()`](../../../apps/web/src/app/api/prm/requests/[id]/route.ts:17)
  и открыть `PrmRequestDetailsDialog` после проверки доступа серверным роутом.
- Перевести все текущие источники PRM-уведомлений на единый builder ссылки.
- Обработать отсутствующую, удалённую или недоступную заявку предсказуемым
  сообщением, очистив некорректный deep link без цикла повторной загрузки.
- Добавить регрессионные исполняемые тесты для построения ссылки и открытия
  карточки из уведомления.

**Не входит в scope:**

- Создание нового маршрута `/prm/[id]` или отдельной страницы карточки.
- Изменение модели `Notification`, polling или API отметки уведомлений прочитанными.
- Изменение PRM-статусов, согласования, поставок или RBAC.
- Переписывание ссылок уведомлений других модулей.

## Steps

1. Добавить PRM-специфичный чистый helper для построения canonical deep link
   `/prm?requestId=<id>` и покрыть его граничными тестами.
2. Заменить строковые ссылки в обработчике переходов и роуте поставки на helper,
   не меняя адресатов, типы и тексты уведомлений.
3. На реестровой странице разобрать `requestId`, вызвать существующий detail API
   и открыть текущий диалог только после успешного ответа.
4. Реализовать состояния loading/not-found/forbidden и одноразовую очистку
   некорректного параметра с сохранением остальных фильтров URL.
5. Добавить компонентный тест клика по PRM-уведомлению и открытия требуемой
   заявки, а также route/helper тесты, доказывающие отсутствие старого `/prm/<id>`.
6. Выполнить полный набор gates и закрыть story одним Conventional Commit.

## Definition of Done

- [x] Каждое новое PRM-уведомление содержит canonical ссылку
      `/prm?requestId=<url-encoded-id>`; старый несуществующий формат не создаётся.
- [x] Переход по ссылке открывает детали именно указанной заявки даже если её нет
      на текущей странице пагинации реестра.
- [x] Доступ к deep-linked заявке остаётся серверно scoped существующим detail API;
      клиент не обходит 401/403/404.
- [x] Недоступный или несуществующий `requestId` показывает понятное сообщение,
      удаляется из URL и не вызывает повторный бесконечный запрос.
- [x] Исправление бага начинается с исполняемого регрессионного теста; новое и
      изменённое поведение покрыто тестами в том же коммите, тесты импортируют

- [x] Full gate green: все проверки из `gates:` прошли.
- [x] Story закрыта одним Conventional Commit согласно lifecycle; зависимостей на

## Result

P3 закрыт. Ссылка PRM-уведомления снова открывает карточку заявки.

**Canonical deep link.** Добавлен чистый helper
[`buildPrmRequestDeepLink()`](../../../apps/web/src/lib/prm-navigation.ts:1),
возвращающий `/prm?requestId=<url-encoded-id>`: он тримит идентификатор,
кодирует его через `encodeURIComponent` и отклоняет пустое значение. Оба
продюсера уведомлений — смена статуса в
[`executeStatusTransition()`](../../../apps/web/src/lib/prm-transition-handler.ts:128)
и регистрация поставки в
[`POST()`](../../../apps/web/src/app/api/prm/requests/[id]/deliveries/route.ts:232)
— переведены на helper. Строковых литералов `/prm/<id>` в дереве не осталось;
адресаты, типы и тексты уведомлений не менялись. Новый маршрут `/prm/[id]` не
создавался — deep link ведёт на существующий реестр.

**Открытие карточки.** [`PrmRegistryContent()`](../../../apps/web/src/app/prm/page.tsx:86)
читает `requestId` из `useSearchParams()` и загружает заявку отдельным запросом
к существующему [`GET /api/prm/requests/[id]`](../../../apps/web/src/app/api/prm/requests/[id]/route.ts:17),
поэтому карточка открывается независимо от текущей страницы пагинации и от
активных фильтров. Доступ остаётся серверно scoped: клиент не обходит
401/403/404, а лишь отображает результат. Ответы 401/403, 404, прочие ошибки,
сетевой сбой и некорректный JSON дают отдельные понятные сообщения, после чего
`requestId` удаляется из URL с сохранением остальных query-параметров.

**Устойчивость загрузки.** Эффект ключуется на строковом значении `requestId`, а
не на нестабильной идентичности объекта `searchParams`, поэтому повторные
рендеры не порождают лишних запросов. Монотонный токен поколения отбрасывает
устаревший ответ при смене `requestId` и при размонтировании, а реестр
in-flight запросов схлопывает двойной вызов эффекта React 18 Strict Mode в один
сетевой запрос. Кэшируется только незавершённый промис — он удаляется сразу
после разрешения, поэтому ни данные, ни отказ в доступе не переиспользуются:
повторный переход по той же ссылке всегда выполняет свежий запрос. Очистка
deep link выполнена единой точкой выхода, поэтому закрытие карточки и любые
действия (приёмка, отправка, согласование, отмена) не приводят к повторному
открытию диалога и не зацикливают загрузку.

**Тесты.** Регрессия закрыта исполняемыми тестами, импортирующими
production-модули: граничные тесты helper'а
([`prm-navigation.test.ts`](../../../apps/web/src/lib/prm-navigation.test.ts:1)),
route-тесты, сверяющие `link` уведомления с результатом helper'а для submit,
approve и приёмки, компонентный тест перехода из
[`NotificationCenter`](../../../apps/web/src/components/layout/NotificationCenter.test.tsx:1)
и набор тестов реестра
([`page.test.tsx`](../../../apps/web/src/app/prm/page.test.tsx:1)), покрывающих
открытие карточки, дедупликацию под `StrictMode`, повторную загрузку после
возврата по ссылке, отбрасывание устаревшего ответа при гонке, сохранение
неотносящихся query-параметров и все ветви ошибок.

**Гейты.** Все проверки из `gates:` прошли независимую верификацию: lint, `tsc`,
`pnpm test`, component suite, coverage, quality baseline, route-test coverage,
static security policies, theme tokens, doc links, а также production build.
Пороги покрытия и качества не понижались. Актуальные значения — в
[`docs/quality/COVERAGE_BASELINE.md`](../../../docs/quality/COVERAGE_BASELINE.md)
и [`docs/quality/QUALITY_BASELINE.md`](../../../docs/quality/QUALITY_BASELINE.md);
отчёты перегенерированы в этом коммите. Заметная часть их дельты относительно
предыдущей версии — следствие устаревшего снимка, а не изменений P3: baseline не
перегенерировался несколько коммитов, поэтому число анализируемых файлов и
метрики подтянулись к фактическому состоянию репозитория.
