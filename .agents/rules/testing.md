# Обязательное тестирование нового кода — EMS-Platform

> Обновлено: 2026-09-02
>
> **Фактические метрики покрытия здесь не публикуются.** Единственный
> источник — генерируемый файл
> [`docs/quality/COVERAGE_BASELINE.md`](../../docs/quality/COVERAGE_BASELINE.md)
> (`node scripts/check-coverage.mjs --report`). Пороги заданы только в
> [`scripts/check-coverage.mjs`](../../scripts/check-coverage.mjs).
>
> Этот файл описывает **обязанность автора кода**, а не текущее состояние
> репозитория. Правила запрета тавтологических тестов и предкоммитный
> чек-лист — в [`code_quality.md`](code_quality.md) §9.

---

## 1. Базовое правило

**Весь новый код, содержащий поведение, обязан сопровождаться
исполняемым тестом в том же коммите.** Тест — часть определения
«функциональность готова», а не отдельная последующая задача.

Правило распространяется на:

| Категория | Что покрывается | Где лежит тест |
|---|---|---|
| API-роуты (`app/api/**/route.ts`) | success, validation-failure, 401, 403, отказ persistence | `apps/web/src/lib/__tests__/` |
| Доменные сервисы (`lib/*-service.ts`, `lib/**`) | ветвления бизнес-правил, границы, отказы | рядом с модулем или в `__tests__/` |
| Чистая логика (сортировки, фильтры, валидаторы, расчёты) | классы эквивалентности и краевые значения | рядом с модулем |
| Пакеты `packages/auth`, `packages/shared` | публичные экспорты | рядом с модулем |
| React-компоненты с логикой (условия, обработчики, состояние) | наблюдаемое поведение, а не разметка | `__tests__/` рядом с компонентом |
| Схема Prisma / миграции | — (проверяется миграционным прогоном) | не требуется |

**Исключения — только эти:**

* чистая разметка без ветвлений (presentation-компонент без условий);
* реэкспорт-барели (`index.ts`), не содержащие логики;
* типы и интерфейсы без рантайм-кода;
* сгенерированный код (Prisma Client).

Исключение не распространяется на компонент, как только в нём появляется
`if`, тернарный оператор в логике (не в стилях), обработчик события с
условием или работа с состоянием.

## 2. Изменение существующего кода

* **Правка бизнес-логики** — обновить или добавить тест, покрывающий
  изменённое поведение. Правка без единого затронутого теста означает, что
  поведение не было покрыто; покрытие добавляется в этом же коммите.
* **Исправление бага** — сначала тест, воспроизводящий баг (красный),
  затем исправление. Без этого нет доказательства, что баг исправлен и не
  вернётся.
* **Рефакторинг без смены поведения** — существующие тесты обязаны
  остаться зелёными **без правок ассертов**. Если для прохождения
  пришлось менять ожидания — это не рефакторинг, а смена поведения.

---

## 3. Критерий пригодности теста

Зелёный тест не равен полезному тесту. Перед коммитом автор обязан
убедиться, что тест **краснеет при регрессии**: временно внести ошибку в
production-код (инвертировать условие, убрать проверку прав, вернуть
константу) и увидеть падение. Затем откатить правку.

Практика показала три способа получить бесполезный зелёный тест:

1. **Тавтология** — локальная копия логики вместо импорта продакшн-модуля.
   Запрещено, разбор и примеры — [`code_quality.md`](code_quality.md) §9.1.
2. **Проверка исходного текста вместо исполнения** — регулярка по коду
   роута не является тестом роута (прецедент:
   [`N4`](../../plans/done/2026-08/N4-replace-source-text-route-tests.md)).
3. **Набор, который не выполнился.** Если `mock.module()` бросает при
   загрузке, `node:test` отчитывается о файле как об **одном пройденном
   тесте**, не выполнив ни одной проверки. Признак: в выводе
   `--test-reporter=spec` нет subtests, а счётчик `tests` подозрительно
   мал. Типовая причина — регистрация двух специфаеров (`../logger` и
   `@/lib/logger`) на один и тот же файл.

Поэтому счётчик тестов проверяется по факту: набор обязан показывать
ожидаемое число subtests, а не только `pass`.

## 4. Обязательные оси для write-роутов

Роут, изменяющий данные, покрывается минимум по пяти осям:

1. успешный сценарий;
2. отказ валидации входа;
3. неаутентифицированный запрос → `401`;
4. аутентифицированный без нужного permission → `403`;
5. отказ persistence → `500` без утечки внутренней ошибки наружу.

Rate limiting проверяется там, где он объявлен в
[`security.md`](security.md). Подключение к PostgreSQL в unit-тестах
запрещено: используется `makePrismaMock()` из
[`route-harness.ts`](../../apps/web/src/lib/__tests__/helpers/route-harness.ts).

## 5. Инструменты (фактический стек)

Jest в проекте **не используется**. Применяются два раздельных раннера:

| Что тестируем | Раннер | Команда |
|---|---|---|
| Логику, сервисы, API-роуты, пакеты | `node:test` + `tsx` | `pnpm test` |
| React-компоненты | Vitest + Testing Library (jsdom) | `pnpm --filter @ems/web test:components` |
| Сквозные потоки | Playwright | `pnpm --filter @ems/web test:e2e` |

Разделение намеренное: Node-раннер не исполняет Vitest-компонентные тесты,
и наоборот. Файл теста попадает в нужный раннер по расположению и
расширению — см. [`scripts/README.md`](../../scripts/README.md).

Перед `pnpm test` обязателен `pnpm db:generate`: без него любой тест,
импортирующий `@ems/database`, падает с
`@prisma/client did not initialize yet`. Это ошибка окружения, а не
регрессия — не «чинить» её правкой тестов.

Покрытие измеряется **только** на версии Node из
[`.nvmrc`](../../.nvmrc): на Node 22 таблица покрытия включает сами
`*.test.ts` и завышает метрики, из-за чего локальный «PASS» может
маскировать красный CI.

## 6. Машинные гейты (что проверяется автоматически)

Ручная дисциплина подкреплена гейтами; они являются нижней границей, а не
заменой правилам выше:

* [`check-route-test-coverage.mjs`](../../scripts/check-route-test-coverage.mjs)
  — падает, если у production-роута `app/api/**/route.ts` нет
  исполняемого теста, который его импортирует. Запускается автоматически
  перед `pnpm test`.
* [`check-coverage.mjs`](../../scripts/check-coverage.mjs) — измеряет line
  coverage, охват файлов и покрытие компонентов, сверяет с порогами.
* [`check-component-test-discovery.mjs`](../../scripts/check-component-test-discovery.mjs)
  — падает, если Vitest находит меньше компонентных тестов, чем зафиксировано.

**Пороги покрытия — ratchet:** их поднимают отдельным коммитом по факту
достижения и **никогда не понижают**, чтобы «протолкнуть» изменение. Если
новый код опустил метрику ниже порога — добавляются тесты, а не
правится порог.

---

## 7. Definition of Done для любой задачи с кодом

- [ ] Новое поведение покрыто исполняемым тестом в том же коммите.
- [ ] Тест импортирует production-модуль, а не копию логики.
- [ ] Проверено, что тест краснеет при внесении регрессии.
- [ ] Набор реально выполняется (subtests видны, счётчик соответствует).
- [ ] Для write-роутов закрыты все пять осей из §4.
- [ ] `pnpm test` — 0 failures; coverage gate не понижен.
