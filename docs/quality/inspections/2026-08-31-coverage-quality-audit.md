## 3. Находки

### 3.1 [BLOCKER] Гейт покрытия красный, `pnpm test` красный

[`backup-script.test.ts`](../../../apps/web/src/lib/__tests__/backup-script.test.ts)
падает обеими проверками:

```
✖ exits non-zero and creates no dump file when the database dump fails
  Error: EPERM, Permission denied: …\Temp\ems-backup-fail-L94sHB (rmSync)
✖ exits zero and creates a non-empty dump file when the database dump succeeds
  AssertionError: backup.sh must exit zero … 1 !== 0
```

Тест запускает `bash scripts/backup.sh` с подменёнными через `PATH`
`docker`/`pg_dumpall`. На Windows-агенте это неработоспособно по двум
причинам: разделитель `PATH` в
[`backup-script.test.ts:40`](../../../apps/web/src/lib/__tests__/backup-script.test.ts:40)
жёстко задан двоеточием (`${mockBinDir}:${process.env.PATH}`), а
`chmodSync(0o755)` на NTFS не даёт бита исполнения. Тест платформо-зависим,
но не помечен ни `skip`, ни условием на `process.platform`.

Следствие: локальный прогон гейта невозможен, разработчик видит красный
`pnpm test` при полностью корректном коде и приучается его игнорировать.

### 3.2 [BLOCKER] Парсер покрытия схлопывает файлы по базовому имени

[`check-coverage.mjs:131-154`](../../../scripts/check-coverage.mjs:131)
собирает `coveredFiles` из TAP-таблицы. Но Node печатает таблицу
**с отступами-деревом**, а не полными путями:

```
ℹ    app                                 |        |          |         |
ℹ     api                                |        |          |         |
ℹ      wms                               |        |          |         |
ℹ       transfers                        |        |          |         |
ℹ        route.ts                        |  31.02 |    73.53 |   73.33 | …
```

Регулярное выражение захватывает `route.ts`, а не
`apps/web/src/app/api/wms/transfers/route.ts`. Замер парсера показал:

| Что | Значение |
|---|---:|
| строк таблицы с процентами | 55 |
| уникальных ключей в `coveredFiles` | 44 |
| потеряно на коллизиях базовых имён | **11** |
| отброшено фильтром `filePath.includes('file')` | 1 (`file-access.ts`) |

Схлопнулись `route.ts`, `get-query.ts`, `patch-update-model.ts`,
`index.ts`, `constants.ts`, `types.ts`. Метрика «охват файлов»
систематически занижена и, что хуже, **нестабильна**: добавление любого
второго `route.ts` не изменит числитель.

Дополнительно фильтр в
[`check-coverage.mjs:148`](../../../scripts/check-coverage.mjs:148)
(`!filePath.includes('file') || filePath.includes('/')`) отбрасывает
любой файл, в имени которого есть подстрока `file` — это `file-access.ts`
сегодня и произвольные файлы завтра.

### 3.3 [BLOCKER] Опубликованный baseline не воспроизводится

[`COVERAGE_BASELINE.md`](../COVERAGE_BASELINE.md) заявляет 78.32 % / 21.68 %
при 80 загруженных файлах. Фактический замер: 67.28 % / 11.92 % при 44.

Расхождение объясняется различием формата вывода `--experimental-test-coverage`
между Node 22 (CI, плоские пути) и Node 24 (локально, дерево с отступами).
Гейт не фиксирует версию Node: нет ни `.nvmrc`, ни поля `engines` в
[`package.json`](../../../package.json). Значение метрики зависит от того,
на какой машине её посчитали, — это не метрика.

Шаг CI
[`ci.yml:92-95`](../../../.github/workflows/ci.yml:92) выполняет
`--report` и затем `git diff --exit-code`, то есть **любое** локальное
обновление baseline на Node 24 гарантированно сломает CI.

### 3.4 [HIGH] Тесты API-роутов измеряют текст исходников, а не поведение

Инвентаризация показала: имена 57 из 85 роутов встречаются в тестах.
Но реально **исполняются обработчики только трёх**:

| Роут | Файл теста |
|---|---|
| `POST /api/auth/login` | [`auth-login-route.test.ts:86`](../../../apps/web/src/lib/__tests__/auth-login-route.test.ts:86) |
| `GET/POST /api/wms/transfers` | [`wms-routes.test.ts:108`](../../../apps/web/src/lib/__tests__/wms-routes.test.ts:108) |
| `GET /api/wms/operations` | [`wms-routes.test.ts:112`](../../../apps/web/src/lib/__tests__/wms-routes.test.ts:112) |

Остальные 54 упомянуты в
[`api-security.test.ts`](../../../apps/web/src/lib/__tests__/api-security.test.ts)
как строковые литералы внутри `readFileSync` + `assert.match`:

```js
// api-security.test.ts:150-154
const source = readRepositoryFile(routePath);
assert.match(source, /from ['"]@\/lib\/logger['"]/);
assert.doesNotMatch(source, /console\.error/);
```

Это статический линт, замаскированный под тест. Он не отличает
импортированный, но неиспользуемый `logger` от вызванного; не проверяет,
что `enforceRateLimit()` вызван **до** обработки запроса, а не в мёртвой
ветке; ломается от переформатирования кода. Такие проверки — задача
ESLint-правила, а не тестового набора; в текущем виде они создают
видимость покрытия 57 роутов при фактических 3.

## 6. Вывод

Фаза `M` решила заявленную задачу — тесты перестали теряться, покрытие
начало измеряться, E2E попал в CI. Но она создала **второй слой ложной
уверенности**, тоньше первого:

1. Метрика покрытия зависит от версии Node и систематически занижена
   из-за дефекта парсинга — то есть baseline в репозитории неверен.
2. 54 из 57 «покрытых» роутов покрыты `readFileSync` + регулярным
   выражением. Формально это тест; по существу — линтер, который
   не выполнит ни строки проверяемого кода.

Практический вывод тот же, что и в предыдущей инспекции, на уровень
глубже: сначала следует привести **измеритель** в состояние, когда его
показания воспроизводимы и означают то, что написано на этикетке
(`N1`–`N3`), и только потом наращивать покрытие. Наращивание покрытия
поверх неисправного измерителя даёт числа, а не защиту.
