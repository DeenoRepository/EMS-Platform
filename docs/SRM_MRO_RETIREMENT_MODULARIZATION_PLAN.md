# План передачи: вывод прототипов SRM/MRO и модуляризация EPS/WMS

Дата: 2026-09-06. Статус: план, реализация НЕ начата.

## Goal of next session

Вывести незавершенные SRM и MRO из активного приложения, сохранить действующие данные и поведение EPS/WMS, затем получить модульный монолит с проверяемыми границами. Обеспечить проверяемый путь обновления существующей PostgreSQL и отката приложения.

Пользователь подтвердил, что SRM/MRO являются прототипами. Документ не разрешает удаление производственных данных, запуск команд на production, автоматическое исправление исторических остатков или развертывание без отдельного согласования. Первый агент выполняет безопасные изменения в репозитории и готовит проверяемые артефакты; эксплуатационные действия требуют подтверждения владельца системы.

### Неприкосновенные ограничения

1. Первый функциональный релиз не меняет физическую схему БД. Сохранить все существующие модели Prisma, таблицы, столбцы, ограничения, enum-значения и связи, включая прототипы.
2. Не применять сброс БД, принудительную синхронизацию схемы с потерей данных, удаление таблиц, очистку пользователей/ролей и установочное наполнение к действующей БД.
3. Не отменять складские движения, созданные MRO, не пересчитывать остатки и не сбрасывать статусы оборудования автоматически. Ошибочные исторические данные исправляются отдельным согласованным процессом.
4. Сохранить поля паспортов о регламенте ТО, периодичности обслуживания, калибровке, внешних идентификаторах. Тематическая связь с ТО не делает их частью удаляемого прототипа.
5. Не совмещать перенос кода с изменением бизнес-правил. Подтвержденные дефекты исправлять отдельными коммитами и тестами, явно описывающими изменение поведения.
6. Не вводить микросервисы, отдельные БД, отдельные репозитории, HTTP между локальными модулями, динамическую загрузку плагинов и универсальный event bus ради модульности.
7. Не обновлять массово зависимости. Использовать подтвержденные API установленной версии, текущие правила безопасности и общую библиотеку UI.
8. Каждый законченный этап — отдельный Conventional Commit. Не включать чужие изменения. Не выполнять push, deploy, rebase или force-reset без разрешения.

### Целевая архитектура

Один web-хост, одна БД, статическая композиция. Бизнес-модуль владеет сценариями и данными, а не просто каталогом.

| Часть | Владеет | Не должна делать |
|---|---|---|
| Web host | Next.js-маршруты, layout, HTTP-адаптеры, сборка зависимостей | Содержать складские инварианты и писать доменные таблицы напрямую |
| EPS | Паспорта, документы, фото, согласования, импорт и отчеты оборудования | Менять остатки WMS |
| WMS | Номенклатура, склады, ячейки, остатки, операции, перемещения, инвентаризация | Произвольно менять жизненный цикл оборудования |
| Платформенные возможности | Пользователи, идентификация, политики доступа, аудит, настройки, доставка уведомлений | Знать сценарии обслуживания и детали складских расчетов |
| Общий UI | Визуальные компоненты и семантические токены | Подтягивать серверные зависимости или вычислять правила доменов |
| Database infrastructure | Подключение, генерация Prisma, управление схемой и миграциями | Быть публичным API для произвольной записи из всех частей приложения |
| Legacy read-only compatibility | Только необходимое чтение старой истории SRM/MRO для EPS | Синхронизировать, создавать заявки, выполнять ТО или менять остатки |

Начать с двух верхнеуровневых workspace-пакетов EPS и WMS, совместимых с текущими glob-правилами workspace. Точные имена и пути определить в ADR до создания. Не дробить сразу каждый модуль на много пакетов. Внутри различать публичные контракты, прикладные сценарии, бизнес-правила, persistence, UI и тесты. Публичные browser-safe и server-only точки входа должны быть раздельными.

Правила зависимостей:

- Приложение использует публичные точки входа модулей; пакеты не импортируют приложение.
- Межмодульные вызовы проходят через явные контракты. Внутренние файлы соседнего модуля закрыты.
- Только persistence-адаптеры владельца меняют его таблицы. Проверка только по имени импорта недостаточна, если общий Prisma дает доступ ко всем моделям: использовать узкие зависимости и контроль model access.
- Доменные правила не зависят от Next.js, React и глобального Prisma.
- UI и контракты не подтягивают Prisma, LDAP, файловую систему, секреты или серверные конфигурации.
- Центральные технические сервисы не зависят от бизнес-модулей; хост собирает каталоги прав и навигации из описаний модулей.
- Внешние ключи и общая транзакция допустимы. Владельца связи оборудования и запчасти определить отдельно, а не делить запись между EPS и WMS.

Задачи:

1. Определить владельцев паспортов, тегов, custom fields/sections, документов, фото, согласований и шаблонов отчетов.
2. Перенести рабочие сценарии за контракты без изменения ID, путей файлов, форматов сохраненных custom fields и поведения импорта.
3. Для файлов сохранить проверки доступа, безопасное разрешение путей, связь метаданных и физического хранилища. Не переносить blobs в рамках архитектурного изменения.
4. Изолировать операции смены жизненного цикла оборудования и согласований. Не давать WMS изменять статусы напрямую.
5. Сохранить legacy read-only слой истории отдельно от доменного ядра EPS. Не позволять ему стать новым универсальным shared-сервисом.
6. Декомпозировать большие страницы по сценариям, переиспользовать shared UI, сохранить URL, query-параметры, пагинацию и пользовательские действия.

Приемка: бизнес-тесты EPS не требуют Next.js, импорт и сохраненные отчеты совместимы, UI не зависит от ORM и серверных секретов, активные SRM/MRO-процессы отсутствуют.

### Этап 5 — упростить платформу и включить архитектурные ограничения

Задачи:

1. Выделить или переиспользовать независимый UI-пакет так, чтобы модули не импортировали приложение. Не дублировать существующие контролы при переносе.
2. Уменьшить shared: доменные DTO, права и отображение статусов отдать владельцам; платформенные примитивы оставить общими. Временные экспорты совместимости вести списком, не допускать циклов.
3. Ввести минимальное статическое описание модулей: идентификатор, навигация, права, настройки, доступность. Не нужен динамический lifecycle движок.
4. Явно определить серверную политику временного отключения оставшихся модулей. Скрытие UI не является авторизацией.
5. Унифицировать транспортные проверки доступа, валидации и ошибок без массового изменения правил RBAC. Найденные fail-open и CSRF-проблемы из старого кода вести отдельно с тестами; не считать их устраненными от переноса файлов.
6. Настроить автоматические проверки: запрет импорта приложения из пакетов, внутренних частей соседнего домена, серверного кода из клиентской точки входа, записей чужих моделей; отсутствие циклов; ограничения публичных exports.
7. Добавить lint/typecheck/test/build задачи модулей и необходимые зависимости генерации Prisma. Проверить чистую CI-сборку и Docker-контекст с новыми пакетами.
8. Архитектурные исключения временно зафиксировать узким allowlist. Запретить новые нарушения сразу и сокращать список по этапам. Не устанавливать глобальные исключения для всего приложения.

Приемка: намеренно добавленный запрещенный импорт ломает проверку CI; новый файл теста автоматически запускается; server-only зависимости не входят в клиентский bundle; сборка выполняется с чистого checkout.

### Этап 6 — подготовить и проверить обновление действующей установки

Выполнять параллельно проектированию, завершить до любого production-релиза.

1. Разделить fresh install и upgrade. Установщик не должен применять разрушительную синхронизацию к существующей БД. Проверить shell/PowerShell/batch-установщики, Docker entrypoint, compose, setup API и startup-команды — не только найденную строку bare-metal.
2. Для schema-neutral релиза зафиксировать отсутствие DDL и data migrations. Генерация Prisma-клиента не заменяет проверку схемы и не должна выполнять синхронизацию БД.
3. Сравнить фактическую схему production со схемой ожидаемого приложения. При расхождении остановить rollout и создать отдельный план совместимости, не пытаться привести production к старому коммиту автоматически.
4. Если внедряется история миграций, baseline оформить отдельным изменением. Он должен соответствовать реальной проверенной схеме; только после сравнения допустимо отмечать исходную миграцию как примененную. Проверить отдельно пустую БД и существующую установку. Не смешивать baseline с удалением старых таблиц.
5. Подготовить согласованный backup БД и пользовательских файлов, образ старого приложения, параметры развертывания и секреты в защищенном хранилище. Не коммитить резервные копии.
6. На восстановленной копии production отключить внешние исходящие интеграции, использовать изолированные учетные данные. Зафиксировать контрольные значения до обновления.
7. Выполнить deployment rehearsal: обновить образ без DDL, проверить health/login, EPS/WMS, отчеты, файлы и историю. Проверить отсутствие вызовов снятых интеграций.
8. Сравнить данные до/после только установки: число записей, ID/связи, агрегаты и точные остатки по складам/номенклатуре. Тестовые операции выполнять отдельным этапом с отдельно учитываемыми ожидаемыми изменениями.
9. Выполнить rollback rehearsal на старый образ поверх БД после тестовых записей новой версии. Подтвердить совместимость записей; откат образа не отменяет их.
10. Получить одобрение владельца на production-окно, отключение внешних отправителей, правила мониторинга и критерии отката. Не выполнять rollout автоматически по факту зеленого CI.

Приемка: воспроизводимый runbook, подтвержденное восстановление, зафиксированные результаты rehearsal и rollback, отсутствие непроверенных обещаний сохранности данных.

### Матрица обязательных проверок

| Группа | Минимальные сценарии | Доказательство |
|---|---|---|
| Авторизация | Login/logout, прежние роли, legacy-коды прав, запрет чужих операций | Тесты настоящей политики, smoke |
| EPS | Создание/изменение, согласования, документы/фото, custom fields, импорт дубликатов, отчеты | Контрактные и интеграционные тесты, UI smoke |
| WMS | Приход, расход, перемещение по этапам, отказ/возврат, инвентаризация, МОЛ | Реальные сценарии с тестовой БД |
| Транзакции | Недостаток, параллельные списания, повтор запроса, сбой вторичного эффекта | Интеграционные тесты; дефекты отдельно задокументированы |
| История | Старые ТО/заявки, движения MRO, старые шаблоны, ссылки уведомлений | Fixtures и копия действующей БД |
| Вывод прототипов | Прямые API/webhook-запросы, меню, polling, startup, задания | Негативные тесты и runtime-наблюдение |
| Границы | Чужой deep import/model write, пакет → host, server → client | Негативные architecture-тесты |
| Установка | Чистая установка и upgrade отдельно, отсутствие неявного seed/DDL | Логи rehearsal без секретов |
| Откат | Возврат старого образа после новых записей, доступность файлов | Протокол rollback rehearsal |

### Стоп-условия

- Обнаружено запланированное удаление/переименование таблиц или колонок в первом релизе.
- Неизвестно, к какой БД обращается тестовая/установочная команда.
- Production отличается от базы реализации, а последствия не разобраны.
- Сохранился активный путь исполнения SRM/MRO или внешняя синхронизация запускается чтением.
- Меняются остатки, статусы, роли или история от одного запуска обновления без согласованной data migration.
- Нет восстановимой резервной копии и проверенного старого образа перед production.
- Тесты зеленые только после удаления полезных assertions, отключения typecheck или глобальных исключений lint.
- Имеются чужие изменения, которые невозможно отделить от этапа безопасным коммитом.

Остановка production-релиза не обязательно блокирует безопасную работу над кодом. В отчете явно различать реализовано, проверено локально, проверено на копии БД и подтверждено для production.

### Порядок коммитов и отчетность следующего агента

Предпочтительные логические этапы: baseline/ADR → страховочные тесты → вывод прототипов с совместимостью → WMS по срезам → EPS по срезам → shell/shared/CI → upgrade runbook и результаты rehearsal.

Для каждого этапа фиксировать: измененные контракты, наличие/отсутствие изменений схемы и данных, выполненные команды и результаты, оставшиеся исключения, условия отката и hash коммита. Коммиты не должны быть одним массовым переносом всех файлов. При исходно падающих тестах показать разницу baseline, а не объявлять весь проект исправным.

### Definition of Done всей работы

- SRM/MRO не исполняются; все оставшиеся упоминания объяснены allowlist.
- EPS/WMS имеют владельцев данных, публичные контракты, собственные тесты и проверяемые границы.
- Хост не содержит доменных записей в БД и бизнес-инвариантов; клиентский код не зависит от серверной инфраструктуры.
- Старые данные, файлы, ID, остатки и необходимая история сохранены; шаблоны и API обработаны по согласованной политике.
- Первый релиз не меняет физическую схему. Любое последующее изменение БД вынесено в отдельный согласованный план.
- CI воспроизводимо проверяет код, тесты и архитектуру. Снятые прототипы не нужны для сборки.
- Обновление и откат проверены на восстановленной копии действующей установки. Если доступ к ней не предоставлен, работа над кодом может быть закончена, но production readiness остается заблокированной.

## Open decisions

До выполнения соответствующего этапа получить ответы или принять безопасное временное решение с записью в ADR:

1. Какая версия реально работает и какая БД будет обновляться? Кто предоставляет обезличенную схему, миграционный статус и тестовую копию? Пока неизвестно — production заблокирован.
2. Есть ли внешние API-клиенты, отправители webhooks и расписания SRM/MRO? Кто их отключает и когда? Пока неизвестно — не обещать бесшовное удаление endpoint.
3. Нужна ли историческая информация SRM/MRO в паспортах и отчетах? Без ответа сохранять данные и необходимые совместимые read-only поля, не заменять исторические значения нулями.
4. Допустимы ли изменения форматов EPS/WMS API? По умолчанию сохранять текущие контракты и URL.
5. Кому принадлежит связь запчасти и оборудования и какой сценарий гарантирует атомарность? Решить до переноса соответствующей WMS-операции.
6. Какие дефекты поведения нужно исправить сейчас? Дефекты целостности/безопасности выделять отдельно; outbox и новые ограничения БД не добавлять тайно в schema-neutral релиз.
7. Нужен ли runtime-флаг отключения EPS/WMS и как он действует на чтение, запись и интеграции? Не проектировать универсальный plugin framework.
8. Когда можно удалить старые таблицы? По умолчанию не удалять; согласовать хранение истории и период отката отдельно.
9. Вспомогательные ссылки и валидаторы handoff-skill отсутствовали по указанному пути при подготовке плана. Не считать этот документ прошедшим отсутствующие автоматические skill-проверки; использовать доступные проверки Markdown/Git и ручной review без утечки секретов.

Темы прежнего обзора о переписывании внутренних SRM-адаптеров, нормализации их аналитики и улучшении MRO-сервисов намеренно исключены из реализации: пользователь выбрал вывод прототипов, а не их доработку. Эти наблюдения остаются контекстом, не backlog текущей задачи.

## Skills to use

Следующий агент выбирает один наиболее подходящий skill для конкретного этапа и соблюдает текущие правила выбора, а не загружает весь список одновременно:

- **zero-hallucination-coder** — многофайловый перенос с картой зависимостей, проверкой API и поэтапной верификацией.
- **senior-architect** — ADR границ, владение данными, публичные контракты и контроль зависимостей.
- **senior-backend** — транзакции EPS/WMS, persistence, авторизация и безопасная совместимость БД.
- **senior-qa** — тесты реальных сценариев и защита от регрессий при удалении/переносе кода.
- **senior-frontend** — разделение shell/UI, перенос страниц и использование существующих общих компонентов.
